Read the run backwards

The last message an agent sends is the only part of the run your customer ever reads.

So that is where we start every investigation now. Not at the system prompt, not at the first tool call, and not at the span with the highest latency. At the answer.

Most teams read a trace the way it was recorded, top to bottom. It feels natural because that is the order things happened in. It is also the slowest way to find a wrong answer, because a long run spends most of its steps doing things that went fine.

A support agent that handled a refund request in forty steps might have one step that went wrong. Reading forwards, you wade through thirty-nine good steps hoping to recognise the bad one when you reach it. Reading backwards, you begin with the thing the customer saw and ask one question at a time until it leads you there.

List what the answer claims

Before opening a single span, write down every claim the final answer makes. Not a summary of it. The claims, one per line, as plainly as you can put them.

An answer like "Your refund of $48 has been issued and should reach your card in three to five days" makes three claims: an amount, an action that already happened, and a timeline. Each one has to have come from somewhere in the run.

Facts it states

Amounts, names, dates, order numbers, policy details. Any of these could have come from a tool result, from the conversation, from the system prompt, or from nowhere at all. The last case is the one you are hunting for.

Actions it reports

"Issued", "cancelled", "updated", "sent". An action claim is only true if a tool call that performs that action ran, succeeded, and returned something that says so. A tool that timed out and then got no retry is the classic way to produce a confident sentence about something that never happened.

Walk each claim to its source

Now open the trace, and for each claim find the latest step that could have produced it. Work from the end of the run towards the start, and stop at the first step that supports the claim.

Three outcomes are possible for each claim:

  • Supported. A tool result or a user message says exactly this. Move on.
  • Stale. Something said this earlier, but a later step changed it, and the answer used the old value.
  • Unsupported. Nothing in the run says this. The model filled the gap.

In practice the walk is short. Most answers make three to six claims, and you are only ever comparing a sentence against a handful of tool outputs, not reading the whole run.

One run, end to start

Here is the run that made us change how we work. A billing agent told a customer their plan had been downgraded and the difference credited. The customer wrote back two weeks later asking where the credit was.

Forwards, the trace looked healthy: forty-one spans, no exceptions, every tool returned a 200, total latency under nine seconds. Two people had looked at it and marked it fine.

Backwards, it took four minutes. The answer claimed a credit. We looked for a create_credit call and found one at step 33, which returned a 200 with a body of {"status": "queued"}. Nothing after it ever checked the queue. The agent read "queued" as "done", and the credit job failed silently overnight on a currency mismatch.

The run never lied about what the tool returned. It lied about what the return meant, and only the answer showed that.

Why forwards reading misses it

Reading forwards, step 33 looks like a success, because by its own standard it was one. The tool did what it said. The problem only exists in relation to a sentence written eight steps later, and you have not read that sentence yet when you pass step 33.

This is the general shape of a quiet failure. The bad step is never bad on its own. It is bad relative to something the agent says or does afterwards, so the only reliable way to see it is to already know what came afterwards.

What Sift does with this

Sift runs this walk on every production run. It extracts the claims from the final answer, links each one to the step that supports it, and flags any claim with no support or with stale support. When the same unsupported claim shows up across many runs, those runs are grouped into one issue so you fix a cause once.

You can still read a run by hand whenever you want, and you should. But you will start from the claim that broke, not from step one.
