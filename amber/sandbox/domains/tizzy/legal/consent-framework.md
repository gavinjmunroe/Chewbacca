# Consent Framework

**Document Purpose:** Detailed design and implementation guidance for Tizzy's consent mechanism, ensuring legal compliance, ethical responsibility, and social acceptance.

**Status:** Core Product Design - Non-Negotiable
**Owner:** Product + Legal + Engineering
**Last Updated:** 2026-02-13

---

## Overview

Consent is not a legal checkbox. Consent is a product design challenge that determines whether Tizzy is trusted or rejected.

**The Core Challenge:**
- **Legal Requirement:** Many U.S. states require all-party consent for recording conversations
- **User Need:** Discretion to avoid stigma and bullying
- **Bystander Right:** Others must know when they're being recorded
- **Social Acceptance:** Consent mechanism must be usable in real-world contexts

**The Tizzy Philosophy:**
We do not hide recording. We hide stigma.

This document defines the consent mechanism: what modes exist, how users obtain consent, how consent is logged and audited, and how to make it socially acceptable.

---

## Consent Modes

Tizzy operates in one of three consent modes at any given time. The mode determines what is captured and what legal/ethical obligations apply.

### Mode 1: Muted (No Capture)

**What It Is:**
Device is not capturing any audio. Microphone is powered off or input is blocked.

**Use Cases:**
- Private conversations where user wants absolute privacy
- Sensitive contexts (therapy for the user, family arguments, confidential settings)
- User forgot to unmute and is not using device
- Emergency mute (domestic violence safety, privacy emergency)

**Legal Status:**
No recording, no consent required.

**Technical Implementation:**
- Physical mute button on device (hardware-level mute preferred)
- Haptic confirmation when muted/unmuted (distinct vibration patterns)
- Visual indicator: LED off (if using LED), app shows "MUTED" in large text
- State persists across power cycles (device remembers if it was muted)

**User Controls:**
- Single press of mute button: Toggle mute on/off
- Long press of mute button: Silent mute (no haptic feedback for discretion)
- App-based mute toggle (for when device is not easily accessible)
- Scheduled quiet hours (auto-mute during set times)

**Logging:**
- Log mute/unmute events with timestamps
- Privacy dashboard shows: "Device muted X% of time this week"

**Design Principle:**
Mute must be instant, obvious, and foolproof. User must always know device state.

---

### Mode 2: Self-Only (Wearer Voice Only)

**What It Is:**
Device captures and analyzes wearer's voice/behavior only. Bystander speech is processed for conversational context but not stored.

**Use Cases:**
- Public environments where obtaining consent is impractical (bus, store, classroom with many people)
- Initial usage before user is comfortable asking for consent
- Contexts where user wants coaching on their own behavior without recording others
- Default mode for most users

**Legal Status:**
Generally compliant with one-party consent laws (wearer is consenting party). May have limitations in all-party consent states if conversation is "private" (context-dependent).

**What Is Captured:**
- Wearer's voice (raw audio in circular buffer, features/embeddings to cloud)
- Wearer's prosody, pacing, intensity, timing
- Wearer's turn-taking patterns
- Conversational context cues (did other person ask a question? seem confused?)

**What Is NOT Captured/Stored:**
- Bystander voice recordings (not saved)
- Bystander transcripts (not generated by default)
- Bystander identity or personal information

**Technical Implementation:**
- Speaker diarization runs on-device
- Tag speaker role: "wearer" vs "other_1", "other_2"
- Process wearer audio: Extract features, send to cloud
- Process bystander audio: Extract minimal context (question vs statement, confused tone, etc.), then discard
- Do not store bystander audio in circular buffer beyond immediate processing

**User Controls:**
- User can set self-only as default mode
- User can switch to consented mode when appropriate
- App shows: "Self-Only Mode: Only your voice is being saved"

**Logging:**
- Log conversation session as "self-only mode"
- Track environment tag (home, school, therapy, public, work)
- Track bystander count estimate (for product analytics, not surveillance)

**Design Principle:**
Self-only mode is the privacy-maximizing default. It provides coaching value while minimizing bystander impact.

**User Education:**
- Explain self-only mode in onboarding: "We focus on your patterns, not recording others"
- Provide guidance on when self-only is appropriate vs when consent is needed
- Remind users: Even in self-only mode, you're capturing audio in public. Be thoughtful about contexts.

---

### Mode 3: Consented Conversation (Full Multi-Party Capture)

**What It Is:**
Full capture of multi-party conversation with consent obtained from other participants.

**Use Cases:**
- One-on-one conversations with friend, family member, therapist (consent obtained verbally or via card)
- Small group conversations where consent is practical (e.g., 2-4 people)
- Therapy sessions (therapist consents as part of treatment)
- Family conversations at home (family members are ongoing consenting parties)
- Structured practice/coaching sessions

**Legal Status:**
Compliant with all-party consent laws if consent is actually obtained. User is responsible for obtaining consent.

**What Is Captured:**
- All participants' voices
- Full conversation context
- Can generate transcripts (opt-in feature)
- Can save conversation clips for review/sharing (opt-in)

**Consent Requirements:**
User must obtain consent from other participants. Consent can be:
1. **Explicit Verbal Consent:** "I'm wearing Tizzy, a conversation coach. It records our conversation to help me improve. Is that okay?"
2. **Consent Card Shown:** User shows physical card explaining device and asking consent
3. **Known Consenting Party:** Ongoing consent from family member, therapist, close friend (documented)
4. **Implied Consent (limited):** Other person is also using Tizzy or has previously consented and is aware device is present

**Technical Implementation:**
- User must explicitly switch to consented mode (not default)
- App prompts: "Have you obtained consent from everyone in this conversation?"
- User confirms consent obtained
- User selects consent method (verbal, card shown, known party, etc.)
- Device records in consented mode
- Visible indicator active (LED, haptic reminder)

**User Controls:**
- User can switch to consented mode via app or physical button combo
- User can add consent notes post-conversation ("Sarah verbally consented at start of conversation")
- User can review consented conversations separately in app

**Logging:**
- Log conversation session as "consented mode"
- Log consent method (verbal, card, known party)
- Log timestamp of consent event
- Log bystander count estimate
- Associate consent log with conversation session for audit trail

**Design Principle:**
Consented mode requires deliberate user action. It is not the default. The user must think about consent, not stumble into recording others.

## Consent Mechanism: How Users Obtain Consent

### The Social Challenge

Asking for consent to record is socially awkward. Users (especially autistic individuals, especially kids) may:
- Fear rejection or judgment
- Struggle with phrasing the request
- Worry about drawing attention to their device
- Avoid asking and use device inappropriately (legal/ethical risk)

**Tizzy's Responsibility:**
Provide tools, scripts, and support to make consent as easy and socially comfortable as possible.

---

### Consent Tool 1: Verbal Consent Script

**What It Is:**
A short, clear script users can say to obtain consent.

**Design Principles:**
- Short (1-2 sentences)
- Clear and direct
- Non-apologetic (not "sorry to ask," but confident explanation)
- Age-appropriate versions (adult, teen, child)

**Example Scripts:**

**Adult Version:**
"Hi, I'm wearing Tizzy, a conversation coaching device. It records our conversation to help me improve my communication skills. Is that okay with you?"

**Teen Version:**
"Hey, I'm using Tizzy to work on my conversation skills. It's like a coach that records so I can learn. Is it cool if we talk?"

**Child Version (with parent support):**
"I'm using a special helper to learn how to talk better. It listens to us. Is that okay?"

**Professional Version (workplace, interview):**
"I want to let you know I'm using an assistive device called Tizzy that records conversations to provide me with communication coaching. Is that alright with you?"

**Therapist/Clinical Version:**
"As part of my therapy, I'm using Tizzy, a conversation analysis tool. It will record our session to help me work on social skills. Is that okay?"

**Implementation:**
- Provide all versions in app
- User can customize scripts
- Practice mode: User can practice saying the script with AI roleplay or with family before using in real world
- Audio examples: Recordings of scripts being said naturally (user can listen and learn phrasing)

**User Education:**
- Onboarding includes: "How to ask for consent" tutorial
- Video examples of consent being obtained in different contexts
- Tips: Make eye contact, speak clearly, wait for affirmative response

---

### Consent Tool 2: Consent Card (Physical)

**What It Is:**
A credit-card-sized card the user carries and can show to others to explain the device and request consent.

**Design Principles:**
- Professional, premium look (not cheap/flimsy)
- Clear, concise text
- Welcoming tone (not legalistic or cold)
- Contact information for questions/concerns

**Card Design:**

**Front:**
```
[Tizzy Logo]

I'm using Tizzy™

Tizzy is a conversation coaching device that helps me improve my communication skills.

It's recording our conversation so I can review and learn from it later.

Is that okay with you?

Thank you for understanding!
```

**Back:**
```
About Tizzy:
Tizzy is an assistive technology device designed to help people improve real-world conversation skills through voice analysis and coaching.

Your Privacy:
- You can decline. I'll switch to a mode that doesn't record your voice.
- You can request deletion anytime.

Learn more: tizzy.com/consent
Questions or deletion request: support@tizzy.com
```

**Implementation:**
- Provide physical card with device purchase (2-3 cards per user)
- User can order more cards (free)
- Digital version in app (user can show phone screen)
- Customizable: User can add their name, contact info if desired

**Usage Guidance:**
- Show card at start of conversation (or when meeting someone new)
- Leave card visible during conversation (on table, etc.) as ongoing reminder
- If person declines, thank them and switch to self-only mode

---

### Consent Tool 3: In-App Consent Indicator

**What It Is:**
A full-screen or prominent in-app display that says "Recording in Progress" and explains the device. User can show this to bystanders as a consent mechanism.

**Design Principles:**
- Large, clear text
- Non-threatening visual design
- Explanation of device and purpose
- Contact information

**Screen Design:**

```
[Tizzy Logo]

🎙️ Recording in Progress

I'm using Tizzy, a conversation coaching device, to improve my communication skills.

This conversation is being recorded for my personal coaching and review.

Is that okay?

---

You can decline, and I'll switch modes.
You can request deletion anytime.

Learn more: tizzy.com/consent
support@tizzy.com
```

**Implementation:**
- Accessible via app (one tap to open consent screen)
- Can leave screen on during conversation (keep phone on table)
- Auto-lock disabled while screen is active (stay visible)

**Usage Guidance:**
- Show phone at start of conversation
- Say: "Here's what I'm using" and hand phone to person to read
- Wait for affirmative response before proceeding

---

### Consent Tool 4: LED Indicator (Hardware)

**What It Is:**
A small LED on the device that illuminates when in consented mode, providing passive notice to bystanders.

**Design Principles:**
- Discreet but visible on close inspection
- Not obnoxiously bright (not flashing, not harsh color)
- Warm color (amber, soft green) not cold/alarming (red, blue)
- Positioned on visible part of device (not hidden under clothing)

**Implementation:**
- LED off: Muted or self-only mode
- LED steady on: Consented mode active
- LED behavior configurable (some users may want off if relying on card/verbal instead)

**Usage Guidance:**
- LED is supplementary to verbal/card consent, not replacement
- User still responsible for obtaining active consent
- LED provides ongoing reminder to bystanders (especially if conversation is long or bystanders join mid-conversation)

**Trade-off:**
- **Pro:** Meets legal "notice" requirement, passive/continuous
- **Con:** Draws attention to device, may increase stigma

**Recommendation:**
- Include LED in hardware design
- Allow user to disable LED if they prefer card/verbal methods only
- Market LED as "transparency feature" not "recording indicator" (frame positively)

---

### Consent Tool 5: Haptic Reminder

**What It Is:**
When user switches to consented mode, device gives a distinct haptic pattern as a reminder to obtain consent.

**Design Principles:**
- Distinct from other haptic patterns (not coaching haptics)
- Noticeable but not alarming
- Can be repeated (e.g., every 5 minutes in consented mode as reminder)

**Implementation:**
- Three short pulses when entering consented mode
- Optional: Periodic reminder (every 5-10 minutes while in consented mode)
- User can acknowledge reminder in app ("Consent obtained, stop reminding")

**Usage Guidance:**
- Haptic prompts user to ask for consent before conversation begins
- If user forgets, periodic reminder nudges them to ensure consent is still valid (e.g., new person joined conversation)

## Consent Logging and Audit Trail

### Why Logging Is Critical

**Legal Protection:**
If challenged, user can show they tracked consent appropriately.

**Ethical Accountability:**
Visible consent log encourages responsible use.

**Product Improvement:**
Understand which consent methods work, where users struggle, how to improve.

**Bystander Trust:**
User can show bystander: "Here's the log showing when I obtained consent from you."

---

### What Is Logged

For each conversation session in consented mode:

**Required Fields:**
- `session_id`: Unique identifier for conversation
- `timestamp_start`, `timestamp_end`: When conversation occurred
- `consent_mode`: "muted", "self-only", "consented"
- `consent_method`: (if consented) "verbal_consent", "consent_card_shown", "app_screen_shown", "known_consenting_party", "therapist", "family_member"
- `environment_tag`: "home", "school", "therapy", "public", "work", "other"
- `bystander_count_estimate`: Number of other speakers detected (0, 1, 2, 3+)

**Optional Fields:**
- `user_notes`: User can add notes ("Had verbal consent from Sarah at start of conversation")
- `consent_timestamp`: When consent was obtained (if different from session start)
- `consenting_party_identifier`: Name or pseudonym of consenting party (optional, for user's own records)

**Audit Trail:**
- All consent events logged in immutable, append-only log
- Cannot be edited or deleted (except full account deletion)
- User can review log anytime in privacy dashboard

---

### User Access to Consent Log

**Privacy Dashboard - Consent Audit View:**

**Summary View:**
- Total conversations captured: X
- Breakdown by consent mode:
  - Muted: X%
  - Self-only: X%
  - Consented: X%
- Breakdown by environment:
  - Home: X%
  - School: X%
  - Therapy: X%
  - Public: X%
  - Work: X%

**Timeline View:**
- Chronological list of all conversation sessions
- For each session: Timestamp, duration, consent mode, environment, bystander count
- Tap to see details (consent method, user notes)
- Can filter by mode, environment, date range

**Consent Report Export:**
- User can generate PDF report of consent log
- Use case: Showing to school, therapist, parent, or legal inquiry
- Report includes: Date range, summary stats, detailed log

---

### Bystander Access to Consent Log (Deletion Request)

**Scenario:**
Bystander says: "You recorded me without consent. I want to know when and I want it deleted."

**Process:**

1. **User Identifies Session:**
   - User reviews consent log to find relevant conversation (by date, time, location)
   - User identifies session_id

2. **User Initiates Deletion:**
   - In app, user selects session and chooses "Delete This Conversation"
   - Reason: "Bystander deletion request"

3. **System Deletes Data:**
   - All audio, transcripts, features from that session deleted
   - Deletion is hard delete (not soft delete)
   - Metadata retained in consent log (for audit trail: "Session X deleted per bystander request on [date]")

4. **Confirmation:**
   - User receives confirmation: "Conversation from [date] has been permanently deleted"
   - User can show confirmation to bystander

**Bystander Deletion Request Form:**
- If bystander contacts Tizzy support directly (not via user), support can facilitate
- Bystander provides: Date, time, location, description of conversation
- Support contacts user to verify and request deletion
- User deletes via app, confirms to support, support confirms to bystander

## Known Consenting Parties

### What Is This?

Some people in the user's life will be ongoing consenting parties: family members, therapists, close friends who understand the device and have given blanket consent.

**Use Case:**
User doesn't need to ask for consent every single time with these people. Consent is ongoing.

**Legal Basis:**
Ongoing consent, periodically reaffirmed, documented.

---

### Implementation

**Consenting Parties List in App:**
- User can add people to "Known Consenting Parties" list
- For each person: Name, relationship, date of initial consent, consent reaffirmation dates

**Adding a Consenting Party:**
- User initiates in app: "Add Consenting Party"
- User enters: Name, relationship
- App prompts: "Have you explained Tizzy to [Name] and obtained their consent to record conversations?"
- User confirms: Yes
- App logs: "[Name] added to consenting parties on [date]"

**Using with Consenting Party:**
- When starting conversation with known consenting party, user selects "Consenting Party: [Name]" from dropdown
- Consent mode switches to "consented"
- Consent method logged as: "known_consenting_party: [Name]"
- No need for verbal script or card each time

**Reaffirmation:**
- App reminds user periodically (e.g., every 30-60 days): "Check in with [Name] to reaffirm consent"
- User confirms or removes from list
- This prevents "consent drift" (person forgets they consented, or withdraws consent)

**Removal:**
- User can remove person from consenting parties list anytime
- Future conversations require fresh consent

---

### Special Considerations

**Family Members (Minors):**
- Parents/guardians on consenting parties list (parent has consented for family conversations to be captured)
- Siblings: If minor, parent consent covers; if adult, sibling must consent individually

**Therapists:**
- Therapist consent is part of treatment plan
- Therapist signs consent form acknowledging sessions will be recorded
- User adds therapist to consenting parties list
- Therapist can revoke consent if clinically appropriate

**Close Friends:**
- Friend must be informed about device and consent explicitly
- Friend can be added to list for convenience
- User should check in periodically (consent fatigue is real; friend may forget what they consented to)

## Age-Appropriate Consent

### Minors Using Tizzy

**Challenge:**
Children and teens may not fully understand consent or may feel pressured not to ask (peer pressure, fear of bullying).

**Tizzy's Approach:**

**For Children (Under 13, if applicable):**
- Parent/guardian involved in consent education
- Simplified consent script
- Consent card is primary method (child shows card, doesn't need to explain verbally)
- Device may auto-start in self-only mode (safest default)
- Parent can review consent log to ensure child is using responsibly

**For Teens (13-17):**
- Age-appropriate consent education
- Peer-friendly consent script ("Hey, I'm using Tizzy to work on conversation skills...")
- Emphasis on respecting others' boundaries (if someone declines, that's okay)
- Privacy controls: Teen can limit parent's view of consent log (age-appropriate autonomy)

**For Young Adults (18+):**
- Full autonomy
- Comprehensive consent education
- Responsibility for legal compliance

---

### Peer Consent (Minors with Minors)

**Special Considerations:**
When minor user is talking to other minors (classmates, friends), consent dynamics are different.

**Best Practice:**
- User should still ask peers for consent (models respectful behavior)
- If peer is very young (under 10), consider also asking peer's parent (if practical)
- Schools may have blanket policies (if Tizzy is used in school, school may require consent from all students' parents)

**Tizzy Guidance:**
- Educate users (and parents) on peer consent expectations
- Provide age-appropriate consent card/script for peer interactions
- Encourage self-only mode in group settings where consent is impractical

## Context-Specific Consent Guidance

Different contexts have different consent norms and legal considerations.

### Home

**Consent Norm:**
Ongoing consent from family members is typical. One-time consent conversation with family, then family is on known consenting parties list.

**Guidance:**
- Have family meeting to explain device
- Demonstrate mute button (family can ask user to mute if they want privacy)
- Add family members to consenting parties list
- Respect family requests to mute (e.g., during arguments, private conversations)

---

### School

**Consent Norm:**
Complex. Multiple stakeholders: teachers, classmates, administrators.

**Guidance:**

**With School Authorization:**
- School has approved device use
- School may require consent from all students' parents (school facilitates)
- User follows school's consent protocol
- Consent mode: Consented (school-authorized)

**Without School Authorization (Personal Use):**
- User may use device but must obtain individual consent
- In classroom: Impractical to get consent from 20+ students → Use self-only mode
- In one-on-one or small group: Obtain verbal consent or show card
- Be mindful of teacher consent (teacher is also being recorded)

**Recommendation:**
For school usage, work through school's policies. Avoid covert use.

---

### Therapy/Clinical

**Consent Norm:**
Therapist consent is part of treatment. Therapist is a known consenting party.

**Guidance:**
- Therapist and client discuss Tizzy use in treatment planning
- Therapist consents to being recorded during sessions
- Therapist may receive Tizzy insights (with client permission)
- Consent mode: Consented (therapist)

**Special Case: Group Therapy:**
- All group members must consent to recording
- Facilitator obtains consent from group at start of session
- If any member declines, user uses self-only mode or mutes

---

### Work

**Consent Norm:**
Professional setting. Consent may be influenced by power dynamics (boss, coworker, client).

**Guidance:**
- Disclose device use to HR/management (assistive technology accommodation)
- Obtain consent from coworkers, clients
- In meetings: Announce at start, get group consent
- If anyone declines, use self-only mode or mute
- Be especially careful with clients/customers (they may feel pressure to consent)

**Legal Note:**
Some states have specific workplace recording laws. User is responsible for compliance.

---

### Public Spaces

**Consent Norm:**
Strangers in public. Consent is often impractical.

**Guidance:**
- Default to self-only mode in public
- If user engages in conversation with stranger (e.g., store clerk, person at bus stop), consider muting or staying in self-only mode
- If conversation is significant and user wants full capture, ask for consent (show card, verbal script)
- Be mindful of expectation of privacy (public bathroom, changing room, medical facility → mute)

**Legal Note:**
Recording in public is generally legal (no expectation of privacy), but social norms matter. Consented mode in public should be rare.

## Consent Failures and Edge Cases

### What If Someone Declines Consent?

**User Response:**
- Thank them for their honesty
- Switch to self-only mode (or mute if appropriate)
- Continue conversation normally
- Do not pressure, guilt, or argue

**App Support:**
- App has quick toggle: "Switch to Self-Only Mode" (one tap)
- Log that consent was declined (for user's own records, not punitive)

**User Education:**
- Normalize consent refusal: "Not everyone will be comfortable, and that's okay"
- Practice handling refusal gracefully

---

### What If User Forgets to Ask for Consent?

**Scenario:**
User is in consented mode, has conversation, then realizes they never asked for consent.

**User Action:**
1. Retroactive consent: User can try to obtain consent after the fact ("Hey, I realized I was recording. Is that okay?")
2. If person consents retroactively: Log as "retroactive consent obtained"
3. If person declines or is unreachable: Delete the conversation

**App Support:**
- Consent mode requires user to confirm consent was obtained
- Periodic reminders while in consented mode ("Did you obtain consent?")
- Easy deletion if consent was not obtained

---

### What If Bystander Discovers They Were Recorded Without Consent?

**Scenario:**
Bystander sees device, asks questions, learns they were recorded, is upset.

**User Response:**
- Apologize sincerely
- Explain the purpose (assistive technology, not surveillance)
- Offer immediate deletion
- Delete the conversation in front of them (show app, delete, confirm)

**Tizzy Support:**
- Bystander can contact Tizzy support for deletion request
- Support facilitates deletion via user
- If user refuses to delete (unlikely), Tizzy can enforce (terms of service)

**Prevention:**
- User education: Emphasize importance of asking for consent upfront
- Consent reminders in app

---

### What If There's a Bystander Complaint or Legal Challenge?

**Scenario:**
Bystander files complaint with school, employer, or even legal action (invasion of privacy, wiretapping).

**Tizzy Response:**
- Legal counsel engages
- Review consent log: Was consent obtained?
- If consent was obtained: Provide evidence (consent log, user attestation)
- If consent was not obtained: Acknowledge failure, delete data, remediate with bystander

**User Liability:**
- User agreed in ToS to comply with recording laws and obtain consent
- User is responsible for misuse
- Tizzy provides tools and education, but cannot prevent all misuse

**Tizzy Mitigation:**
- Strong user education
- Consent reminders
- Easy deletion pathway
- Responsive support for bystander concerns

## Consent Mechanism Usability Testing

### Pre-Launch Testing

**Test with Beta Users:**

**Test 1: Consent Script Usability**
- Can users successfully say the script in real-world contexts?
- Do bystanders understand and respond positively?
- Do users feel socially comfortable asking?
- Iterate on script based on feedback

**Test 2: Consent Card Usability**
- Do users carry the card?
- Do they show it when appropriate?
- Do bystanders read and understand it?
- Does card design feel professional/premium (not cheap)?
- Iterate on card design

**Test 3: In-App Indicator Usability**
- Do users remember to show the app screen?
- Do bystanders understand the screen?
- Is it awkward to hand phone to stranger?
- Iterate on screen design

**Test 4: LED Indicator (if included)**
- Is LED visible but not obnoxious?
- Do bystanders notice it?
- Does it increase stigma or is it acceptable?
- User feedback on LED usefulness

**Test 5: Consent Mode Switching**
- Can users quickly switch modes?
- Do they understand the difference between self-only and consented?
- Are mode indicators clear?
- Iterate on UI

**Test 6: Consent Logging**
- Can users find consent log in app?
- Do they understand what's logged?
- Is it useful for accountability?
- Iterate on dashboard design

---

### Post-Launch Monitoring

**Metrics:**
- % of conversations in each mode (muted, self-only, consented)
- % of consented conversations with logged consent method
- Bystander deletion requests (should be rare)
- User feedback on consent mechanism (surveys, support tickets)

**Goals:**
- High % self-only usage (privacy-maximizing default)
- Low % consented mode without logged consent (compliance)
- Very low bystander complaints (social acceptance)

**Iterate:**
- If bystander complaints are high: Improve consent education, make indicator more visible
- If users avoid consented mode entirely: May indicate social discomfort; improve consent tools
- If users overuse consented mode without logging: Remind of consent obligations

## Legal Review of Consent Mechanism

### Pre-Launch Legal Checklist

- [ ] **Consent mechanism reviewed by legal counsel with expertise in recording laws** (Owner: Legal, Priority: Critical, Timeline: Pre-launch)
  - Does mechanism meet "notice" requirement in all-party consent states?
  - Are consent modes clearly differentiated?
  - Is user liability for non-compliance clearly communicated?
  - Evidence: Legal memo, approval to launch

- [ ] **Consent logging meets legal record-keeping standards** (Owner: Legal + Engineering, Priority: High, Timeline: Pre-launch)
  - Is log immutable and auditable?
  - Can log be used as evidence if challenged?
  - Evidence: Logging architecture review, legal approval

- [ ] **User agreement includes consent obligations** (Owner: Legal, Priority: Critical, Timeline: Pre-launch)
  - User agrees to obtain consent where required
  - User agrees to comply with state recording laws
  - User acknowledges Tizzy provides tools but user is responsible
  - Evidence: Terms of service, user agreement flow

- [ ] **Bystander deletion process is legally sufficient** (Owner: Legal, Priority: High, Timeline: Pre-launch)
  - Fast response time (24-48 hours)
  - Hard deletion (not soft delete)
  - Confirmation provided
  - Evidence: Deletion workflow, legal review
