A retry loop that passed every health check

June 3, 2026
Mara Lindqvist Founding engineer, Sift
5 min read
  1. Everything was green
  2. What the loop looked like
  3. Why nothing caught it
  4. The check we added

For a week, a scheduling agent searched the same calendar nineteen times in an average conversation, and every dashboard said it was healthy.

Error rate was flat because each search succeeded. Latency rose, but slowly, and inside the alert threshold. Cost went up by a third, which someone noticed on the invoice at the end of the month.

What the loop looked like

A prompt change had told the agent to "confirm availability before booking". It did. It searched, found a free slot, and then, before booking, searched again to confirm. The second search returned the same slot, which it took as a reason to confirm once more.

Most conversations eventually ended because the context filled and an older instruction to book took over. The customer got a booking. Nothing looked wrong from the outside.

Why nothing caught it

Every metric we had was about single steps: did this call fail, was this call slow. A loop is not visible in any single step. It is only visible as a pattern across steps in one run: the same tool, the same arguments, the same result, again.

The check we added

Sift now looks for repeated calls inside a run. Two calls with identical arguments and identical results, with no change to the conversation between them, count as one repeat. Three repeats in one run raise a flag with the step numbers attached.

It is a deliberately plain rule. It fires rarely, and when it does, it is almost always right.
